一、修复角色停用后的缓存权限隔离
问题位置：
backend/app/services/search.py
当前 permission_cache_scope() 使用所有角色 ID：
roles = "-".join(sorted(str(role.id) for role in self.user.roles))
角色停用后，角色 ID 没变，缓存 Key 可能仍然相同，导致用户继续命中停用前生成的包含受限资料的回答。
修改要求：
1. 缓存权限范围只包含启用角色：
enabled_role_ids = sorted(
    str(role.id) for role in self.user.roles if role.enabled
)
2. 缓存指纹必须在以下情况发生变化：
   - 用户角色增加或删除。
   - 角色启用或停用。
   - 用户部门变化。
   - 部门启用或停用。
   - 文档 ACL 增加、删除或权限级别变化。
   - 文档可见范围变化。
   - 文档删除、恢复、启用或停用。
3. 推荐实现明确的权限版本机制，而不是只依赖 ACL 数量和最大创建时间。
可选实现：
- 在缓存指纹中加入启用角色 ID。
- 加入角色的 updated_at。
- 加入部门链上的 updated_at。
- 加入 ACL 的数量、最大时间及内容哈希。
- 或增加全局 permission_version，权限变更时递增。
最低要求是停用角色后旧缓存不能再命中。
测试场景：
1. 用户拥有角色 A。
2. 角色 A 可以访问文档 X。
3. 用户提问并生成缓存答案，引用文档 X。
4. 管理员停用角色 A。
5. 用户再次提出完全相同的问题。
6. 必须重新检索，答案和引用中不得包含文档 X。
7. 重新启用角色 A 后，权限可以恢复，但不得错误复用无权限阶段的缓存。
二、修复会话归档接口
问题位置：
backend/app/api/chat.py
当前接口在 purge=false 时只返回归档成功，没有真正归档：
if purge:
    service.purge(session_id)
    return {"deleted": True}
return {"archived": True}
修改为：
if purge:
    service.purge(session_id)
    return {"deleted": True}

service.archive(session_id)
return {"archived": True}
要求：
- 普通删除：设置 archived_at，不删除会话和消息。
- 永久删除：只有 purge=true 才执行物理删除。
- 必须继续校验会话所有权。
- 普通用户不能归档或永久删除他人的会话。
- 管理员行为按当前产品规则保持不变。
测试：
- 归档后默认会话列表不出现。
- 归档列表中可以看到。
- 恢复后重新出现在默认列表。
- 归档不会删除消息和引用。
- 用户 A 不能归档用户 B 的会话。
- purge=true 才真正删除。
三、补全失败操作审计
相关位置：
backend/app/services/audit.py
backend/app/api/auth.py
backend/app/api/users.py
backend/app/api/departments.py

当前多数接口只在成功后调用 audit_record()，业务异常没有失败审计。
实现目标：
每个关键写操作无论成功或失败，都生成审计记录：
success=true/false
error_code
request_id
user_id
username
action
target_type
target_id
ip_address
detail
建议增加统一包装函数或上下文管理器，避免每个接口重复 try/except。
示例思路：
try:
    result = service.operation(...)
except AppError as exc:
    audit_record(
        audit_session,
        action,
        user=user,
        target_type=target_type,
        target_id=target_id,
        success=False,
        error_code=exc.code,
        request_id=request_id,
        ip_address=ip_address,
    )
    raise
else:
    audit_record(
        audit_session,
        action,
        user=user,
        target_type=target_type,
        target_id=target_id,
        success=True,
        request_id=request_id,
        ip_address=ip_address,
    )
注意：
- 审计写入失败不能回滚已经成功的核心业务。
- 最好为审计使用独立数据库 Session。
- 不能把密码、Cookie、API Key、完整文档正文或完整模型 Prompt 写入审计。
- 不能在异常信息中保存数据库连接密码。
- 422 请求体校验失败如果无法进入路由，可暂不记录，或通过全局异常处理器统一记录。
- 至少覆盖业务层 AppError 和外部服务失败。
必须覆盖的失败审计：
- 登录失败、登录限流。
- 用户创建、修改、启停、重置密码失败。
- 部门和角色管理失败。
- 文档上传、下载、删除、恢复、永久删除、重处理失败。
- 文档权限和外发策略修改失败。
- DeepSeek 请求、成功、失败、被策略阻止。
- Harness 工具调用、审批和写操作失败。
修复退出登录审计用户为空
/api/auth/logout 被认证中间件当作公开接口，因此：
request.state.auth_user
通常没有值。
修改方式之一：
- 中间件允许 logout 不强制登录，但如果 Cookie 存在则尝试解析用户并放入 request.state.auth_user。
- 或在 logout 接口撤销 Session 前，根据 Cookie 查询 AuthSession -> User。
审计记录中应包含实际退出用户，但不能记录原始 Cookie。
四、修复文档版本权限检查
问题位置：
backend/app/services/documents.py
当前 versions() 对向下查询出的子版本没有逐个执行权限检查。
要求：
- 每个返回的文档版本都必须按照当前用户重新执行 PermissionResolver.can_read()。
- 不得因为用户能查看版本 A，就自动允许查看 ACL 不同的版本 B。
- 推荐无权限版本直接从结果中过滤。
- 如果产品需要显示版本存在，可以只返回脱敏元数据，但第一版建议直接隐藏。
- 已软删除版本只有具备权限的用户才能查看。
- 超级管理员保持可查看。
参考实现：
children = list(
    self.session.scalars(
        select(Document).where(
            Document.previous_version_id.in_(frontier)
        )
    )
)

visible_children = []
for child in children:
    if self.resolver is None or self.resolver.can_read(child):
        visible_children.append(child)

values.extend(visible_children)
frontier = [item.id for item in children]
注意：遍历链条可以继续使用全部子节点，但最终返回值只能包含当前用户可读版本，避免因为中间版本不可读而无法找到后续可读版本。
测试：
- 同一版本链包含 COMPANY、ROLE、USER 三种 ACL。
- 普通用户只能看到有权限的版本。
- 无权限版本不能通过版本 API、详情、下载或片段接口访问。
- 超级管理员能看到完整版本链。
